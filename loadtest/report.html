서버는 몇 명까지 버티는가 — 400명 램프 리포트

치매 환자 모니터링 백엔드(FastAPI)에 환자 기기 + 보호자 앱 혼합 부하를 걸어 처리량 한계와 병목을 측정했다. 최초 측정(2026-07-18) 이후 device_token 실제 DB 검증이 추가되며 용량이 눈에 띄게 낮아져 재측정했다.

도구 Locust 2.46.3부하 400 VUs · 램프 10/s · 5분 대상 uvicorn 1-worker호스트 4 vCPU (co-located) 측정일 2026-08-22 (최초 2026-07-18)

결론. 처리량은 ~52 RPS 부근에서 정점(동시 ~210~240명)을 찍은 뒤, 400명까지는 물론 400명을 5분간 유지하는 동안에도 안정화되지 않고 계속 하락한다(정점 52 RPS → 5분 뒤 ~32~40 RPS). 원인은 이전과 동일한 단일 uvicorn 워커(코어 1개 포화) + DB 커넥션 풀 고갈(30)이지만, 이번엔 풀 고갈이 대기 지연을 넘어 QueuePool ... connection timed out 명시적 500 에러(29건)로 실제 요청 실패를 냈다. AI 컨테이너는 여전히 병목이 아니다.

04해결방안 — 효과·순서 순

  1. uvicorn 워커 다중화 효과 ★★★ · 3코어 유휴

    단일 프로세스 → 4워커로 코어를 모두 활용하면 처리량 ~3–4배(≈230–300 RPS). 다만 현재 앱은 단일 프로세스 전제라 그냥 켜면 깨진다.

    ⚠️ 선행 필요: 스케줄러가 워커마다 돌아 알림이 4중 발송되고, 인메모리 GPS 버퍼가 워커별로 갈라진다. → 스케줄러를 별도 프로세스로 분리 + 버퍼를 Redis 공유(또는 배회 detect를 DB 조회 기반)로 먼저 전환한 뒤 gunicorn -k uvicorn.workers.UvicornWorker -w 4.

  2. DB 커넥션 풀 상향 효과 ★★ · 즉효·저위험 · 우선순위↑

    database.py의 pool_size/max_overflow를 올리고 MySQL max_connections(기본 151)와 함께 사이징. 4워커 기준 워커당 풀 × 4 ≤ max_connections (예: 워커당 15+15 → 총 120). 이번 재측정에서 풀 고갈이 지연을 넘어 QueuePool timed out 500 에러 29건으로 실제 요청 실패를 냈으므로, 다른 항목보다 먼저 처리할 가치가 있다.

  3. 배회 detect를 핑 경로에서 분리 효과 ★★ · 쓰기경로 경량화

    지금은 GPS 핑마다 배회 AI를 백그라운드 호출 + DB 세션을 연다. 환자당 N핑/X초 디바운스 또는 스케줄러 주기 실행으로 옮기면 핑당 이벤트루프·DB 부하가 준다.

  4. 폴링 → WebSocket 푸시 효과 ★★ · 읽기부하 감소

    보호자 앱이 /persons·/location·/alerts·/unread-count를 1–2초마다 폴링(전체 요청의 ~절반). 푸시로 대체하거나 주기 상향 + /alerts 캐싱하면 같은 서버로 더 많은 보호자를 수용한다.

  5. 수평 확장 효과 ★★★ · 근본

    ①~④로 앱이 프로세스-safe 해진 뒤 백엔드 컨테이너 N개 + nginx/traefik 로드밸런서, Redis로 버퍼·세션 공유 → 거의 선형 확장.
