서버는 몇 명까지 버티는가 — 400명 램프 리포트

치매 환자 모니터링 백엔드(FastAPI)에 환자 기기 + 보호자 앱 혼합 부하를 걸어 처리량 한계와 병목을 측정했다. 08-22 재측정에서 드러난 단일 uvicorn 워커 CPU 포화를 gunicorn 4워커 + Redis(GPS 버퍼·WebSocket 팬아웃 공유) 전환으로 해소한 뒤 다시 측정한 결과다.

도구 Locust 2.46.3부하 400 VUs · 램프 10/s · 5분 대상 gunicorn 4-worker(UvicornWorker) + Redis호스트 4 vCPU (co-located) 측정일 2026-08-23 (08-22 재측정 · 최초 2026-07-18)

결론. 단일 워커 CPU 포화를 4워커로 해소하자 처리량이 램프 중 ~90 RPS까지 오르고(뚜렷한 무릎점 없이 400명까지 계속 상승), 400명 유지 5분간 QueuePool 타임아웃 500 에러가 완전히 사라졌다(08-22엔 29건). 400명 p95는 15s → 5.1s로, p50은 6.0s → 2.0s로 개선됐다. 다만 실패율은 0.27%→1.81%로 소폭 늘었는데, 원인이 DB 풀 고갈이 아니라 같은 호스트에서 locust·backend가 CPU를 경쟁하며 생기는 것으로 보이는 RemoteDisconnected(연결 끊김) 계열이라 성격이 다르다. SLA(p95<200ms) 용량 자체는 ~90명으로 08-22와 비슷 — 이번 조치는 "과부하 시 완전히 무너지지 않는" 문제를 풀었을 뿐, 저부하 SLA 상한을 올리진 못했다.

DB 풀만 올려본 실험(반영 안 됨): pool_size 10→70, max_overflow 20→30로 재측정했더니 처리량이 오히려 29 RPS로 더 떨어지고 QueuePool 타임아웃도 재발했다. 모니터링 결과 DB CPU는 그때도 여유(12~17%)였고 backend CPU만 그대로 1코어 포화 — 즉 병목은 처음부터 DB가 아니라 CPU였고, 풀을 키운 건 이미 포화인 CPU 앞에 더 많은 요청을 줄 세운 것뿐이었다(원래 작은 풀이 오히려 초과 요청을 빨리 실패시키는 백프레셔 역할을 하고 있었음). 그래서 풀 크기는 원복하고 워커 확장을 먼저 진행했다.

4워커+Redis 전환 시 함께 처리한 것: 인메모리 GPS 버퍼(core/buffer.py) → Redis 리스트, 스케줄러(하트비트·낙상판정·배회enroll) → 별도 프로세스(baguetteboost-scheduler)로 분리(워커마다 중복 실행되던 것 제거), WebSocket 알림 → Redis Pub/Sub 팬아웃(어느 워커가 소켓을 들고 있든 전달되도록). 세 가지 모두 멀티워커에서 프로세스 로컬 메모리에 있으면 깨지는 상태였다.

04해결방안 — 진행 상황

  1. DB 커넥션 풀 상향 ✅ 시도 · 반영 안 함(원복)

    가장 먼저 시도했으나(pool_size 10→70, max_overflow 20→30) 처리량이 29 RPS로 더 떨어지고 QueuePool 타임아웃도 재발했다. DB CPU는 그때도 여유였고 backend CPU만 그대로 포화 — 진짜 병목이 CPU였다는 걸 이 실험으로 확인하고 원복, 순서를 ②로 바꿨다.

  2. uvicorn 워커 다중화 ✅ 완료 · 효과 ★★★

    gunicorn -k uvicorn.workers.UvicornWorker -w 4로 전환, CPU가 1코어(105%) → 4코어 분산(~330%)으로 실제로 늘었다. 선행 과제였던 스케줄러 중복 실행(→ 별도 baguetteboost-scheduler 프로세스로 분리), GPS 인메모리 버퍼·WebSocket 알림(→ 둘 다 Redis로 공유: 버퍼는 리스트, 알림은 Pub/Sub 팬아웃)까지 함께 처리했다.

  3. 배회 detect를 핑 경로에서 분리 다음 순서 · 효과 ★★ · 쓰기경로 경량화

    지금도 GPS 핑마다 배회 AI를 백그라운드 호출한다(이제 Redis 버퍼 조회가 추가돼 핑당 비용이 인메모리 시절보다 약간 늘었다 — 이번 측정에서 SLA<200ms 용량이 08-22와 그대로 ~90명인 이유 중 하나로 의심됨). 환자당 N핑/X초 디바운스 또는 스케줄러 주기 실행으로 옮기면 핑당 이벤트루프·Redis·DB 부하가 준다.

  4. 폴링 → WebSocket 푸시 효과 ★★ · 읽기부하 감소

    보호자 앱이 /persons·/location·/alerts·/unread-count를 1–2초마다 폴링(전체 요청의 ~절반). 푸시로 대체하거나 주기 상향 + /alerts 캐싱하면 같은 서버로 더 많은 보호자를 수용한다.

  5. 수평 확장 효과 ★★★ · 근본

    ③~④ 이후 백엔드 컨테이너 N개 + nginx/traefik 로드밸런서 — 버퍼·알림이 이미 Redis로 공유되므로 이번 단계 덕분에 수평 확장 자체의 걸림돌은 사라졌다.

방법론 · 한계
  • 혼합 부하: 환자 기기(device_token 인증 GPS 핑 + 가끔 IMU 낙상) + 보호자 앱(로그인 후 조회 폴링). 시드 보호자 50 · 환자 200.
  • 22,561건 중 실패 409건(1.81%): 전부 RemoteDisconnected(연결 끊김) — 08-22의 QueuePool 타임아웃 500은 이번엔 0건. 서버 애플리케이션 로그에 대응하는 예외가 없어, DB/애플리케이션 문제라기보단 co-located 테스트 환경(아래 항목)에서 오는 전송 계층 문제로 추정된다(확정은 아님 — 별도 호스트 재측정으로 확인 필요).
  • 공존 실행 주의: locust·backend·db·AI·redis·scheduler 가 같은 4코어 호스트에 함께 떠 CPU를 경쟁했다(07-18/08-22와 동일 조건). 따라서 절대 수치는 여전히 보수적 하한이며, "4워커 전환이 CPU 포화·QueuePool 타임아웃을 실제로 해소했다"는 상대적 결론은 확고하다.
  • Redis Pub/Sub을 통한 WebSocket 팬아웃은 수동 테스트(연결된 소켓에 redis-cli PUBLISH로 직접 발행)로 4워커 모두가 구독 중임을 확인했다 — locust 시나리오 자체는 WebSocket을 다루지 않는다.
  • 이 리포트가 "최신 상태"로 유효한 기간: 다음에 telemetry 경로나 워커 수·DB 풀 설정을 바꾸면 이 수치도 다시 stale해진다 — 그 시점에 재실행 권장.
